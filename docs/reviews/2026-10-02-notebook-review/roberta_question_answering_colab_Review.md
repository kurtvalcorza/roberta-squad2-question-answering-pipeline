## Executive assessment

**Readiness: Needs revision.** The default path is technically careful and has documented clean-runtime evidence for this exact blob (Kaggle Tesla T4, 2026-09-19). The snapshot, corpus and adapter are all digest-checked, the split is article-disjoint, and the export reloads with parity. Four problems stop it from being ready:

1. **The adaptation result is misread (RQA-M2).** The notebook's headline is that fine-tuning "roughly doubles held-out F1" (12.38 → 26.49). The frozen model with its null answer switched off, which needs no training, already scores **F1 25.28 / exact-match 16.75** on the same 400 test questions (CPU probe). This corpus has no unanswerable questions, so nearly all of the measured gain comes from the model no longer saying "no answer". Better reading accounts for at most about 1 F1 point, and with one split and no dispersion estimate that point is not established.
2. **Run all needs a manual restart** after the in-kernel pip install. The recorded run needed one (RQA-M1).
3. **Reruns never reset to the pretrained model.** The optional experiments and the documented BYOD rerun therefore report adapted scores as "frozen". A `TRAINABLE_ENCODER_LAYERS = 1` rerun exports an artifact that fails its own reload-parity assertion: 25/40 answers matched in the probe (RQA-M3).
4. **The BYOD branch fails at Section 4 for representative inputs.** A set with unanswerable questions can crash the probe block with `IndexError` (3 of 10 seeds), and anything under about 50 records is refused although the stated minimum is 8 (RQA-M4, RQA-M5). The guided layer is also missing (RQA-M6).

#### RQA-M1 — Run all needs a manual restart after the in-kernel pip install

- **Cell/section:** Section 1, cell 3.
- **Observed:** the cell `pip install`s `torch==2.14.0`, `transformers==4.57.6`, `numpy==2.5.3` and others into the live kernel. If a loaded distribution changed, it raises `RuntimeError('… Restart the runtime, then rerun from the top.')`.

- **Evidence:** documented execution evidence. `docs/release-verification.md` records "11/11 code cells ok (**1 restart after install cell**)" for this exact blob on Kaggle T4. The image had torch 2.10.0 / transformers 5.0.0 before the install. Step 4 of the procedure says "an interpreter restart after the install is expected". Source inspection confirms no uv or isolated environment (`results.json` `static.uses_uv = false`).
- **Recommended correction:** adopt the fleet's **uv isolated-environment pattern** in the generator template (`tools/notebook_template.py`, emitted by `tools/build_notebook.py`). A carrier cell bootstraps uv, creates `uv venv --managed-python --python 3.12.12 <ROOT>/env`, installs a hash-locked `requirements.txt` with `uv pip install --require-hashes --only-binary :all:`, and runs the workload in that env, so the kernel's preloaded torch and NumPy are never replaced. #### RQA-M2 — The adaptation "gain" is almost entirely null suppression; the comparison omits the baseline that shows it

- **Cell/section:** Sections 6–8 and Interpretation (cells 16, 18, 20, 21, 24); opening cell 0.
- **Observed:** the notebook frames the experiment as "whether a small in-distribution adaptation … recovers ground on held-out articles". It concludes that the fine-tune "roughly doubles held-out F1 and lifts the answered rate to 100 %". The test split contains **no unanswerable questions**, and the frozen model returns the empty answer for 56.5 % of them. Taking the frozen model's best span instead of the null (no training) gives:

  | Test split, 400 questions | EM | F1 | Answered |
  |---|---|---|---|
  | Frozen (null-vs-span rule) — CPU probe / T4 record | 8.0 / 8.0 | 12.38 / 12.38 | 43.5 % |
  | **Frozen, null disabled (best span always)** — CPU probe | **16.75** | **25.28** | 100 % |
  | Adapted — CPU pre-flight record / T4 record | 17.25 / 16.25 | 26.49 / 25.81 | 100 % |

- **Consequence:** the learner concludes that two epochs of fine-tuning taught the model to read adversarial questions about twice as well. What the data shows is that the model learned to stop abstaining, which a one-line decision change achieves without training. The remaining difference (+1.2 F1 on CPU, +0.5 against the T4 run) is smaller than the unmeasured split-to-split variation. The notebook does say the null decision is "traded away", but it presents the trade as a side effect of a real gain rather than as the gain itself. This is the scientific-validity failure the framework names: the conclusion is not supported by the experiment as designed.
- **Evidence:** direct execution on CPU (probe `model.frozen_forced_span_test_no_null`, which uses the pipeline's own `_runner` and the same softmax and span-length rule as `answer`, excluding `<s>`). The frozen figures reproduce the record exactly (8.0 / 12.38 / 43.5 %). The adapted figures come from documented execution evidence.
- **Recommended correction:** in `src/roberta_question_answering_pipeline/metrics.py`/`pipeline.py`, add a "frozen, forced span" baseline (e.g. `pipe.evaluate(..., allow_null=False)`) and include it in the Section 8 comparison and the exported `comparison`. Rewrite the Section 6/8 and Interpretation prose (template) to separate the null-suppression effect from the span-quality effect. Read F1 on the frozen model's answered subset as well. Either show a configuration where adaptation beats the forced-span frozen model by more than the stated noise, or state plainly that on this corpus it does not. The `assert adapted_test['f1'] > frozen_test['f1']` in cell 21 then needs rethinking too.
- **Acceptance check:** the Section 8 comparison prints a forced-span frozen row. The Interpretation's claim about what fine-tuning achieved is consistent with adapted F1 minus forced-span F1, the null-suppression effect is named as such, and no sentence attributes the full 12.38 → ~26 change to improved reading.
- **Spec:** EVAL10, EVAL15, GDL14 (and framework dimension 3).

#### RQA-M3 — Reruns never reset to the pretrained model; the optional experiments and the BYOD rerun mislabel adapted scores as "frozen", and a layers=1 rerun fails its own parity assertion

- **Cell/section:** Section 7 (cell 19), Section 6 (cell 17), Section 9 (cell 23); "Optional experiments" in cell 24; the BYOD instruction "re-run from that cell" in cell 0.
- **Observed:** `pipe.adapt` trains the existing `pipe` in place and never restores the base. Rerunning cell 19 after a change ("set `TRAINABLE_ENCODER_LAYERS = 1`", "raise `EPOCHS`") or rerunning from Section 4 for BYOD has three effects. Epoch 0, labelled `"frozen model"`, scores the already-adapted model. Section 6's `frozen_test` becomes the adapted model. Training stacks on top of the previous run. With layers=1 after the default run, the adapted block 10 stays in `pipe`, but the artifact only carries block 11 and the head. The reload onto the clean base therefore differs and `assert parity['identical_answers'] == parity['of']` fails.
- **Consequence:** the documented exercises produce wrong comparisons. "Compare the test scores" is comparing a stacked fine-tune against a mislabelled baseline, and the layers=1 exercise ends in an `AssertionError` before the result JSON is written. A BYOD run after the sample run reports the AdversarialQA-adapted model as the "frozen" baseline for the user's data.
- **Evidence:** direct execution on CPU (stand-in sizes, probe `rerun`):
  - True frozen val F1 is 5.24. The second `adapt` call's epoch 0 (`note: "frozen model"`) is **31.19**.
  - A Section-6 rerun after `adapt` printed F1 **20.84** on the 40-question probe set, against a true frozen value of **9.21** (`evaluate` even returns `adapted: True`).
  - Rerunning with layers=1 gives an 18-tensor artifact; after reload, block `10` differs; answers match **25/40**; the max start-logit difference on record 0 is 3.08.
  - Source inspection: `pipeline.py` `adapt` has no reset path, and cell 24 gives no rerun instruction.
- **Recommended correction:** in the template, make cell 19 (and Section 6) start from a fresh base. Either rebuild `pipe = RoBERTaQuestionAnsweringPipeline.from_pretrained(weights_dir=WEIGHTS_DIR)` at the top of Section 6, or add `pipe.reset()` in `pipeline.py` that restores the snapshot tensors. Give the optional experiments and BYOD an explicit "re-run from Section 6 (or 4)" instruction. Alternatively, have `save_artifact` refuse when tensors outside the current trainable set differ from the base.
- **Acceptance check:** run the default path. Then set `TRAINABLE_ENCODER_LAYERS = 1` and follow the notebook's rerun instruction exactly. Epoch 0 val F1 must equal the first run's epoch 0. Section 6 must reprint the frozen 12.38. Section 9 parity must pass.
- **Spec:** SRC2, GDL10, UX7, VER4.

#### RQA-M4 — BYOD with unanswerable questions can crash Section 4 with a raw `IndexError`; the wrong-offset probe can falsely "accept"

- **Cell/section:** Section 4, cell 13, refusal-probe block.
- **Observed:** the probe dictionary is built before the `try` and indexes `splits['train'][0]['answers'][0]`. When the first training record after the seeded split is unanswerable (empty `answers`, which the notebook invites: "add unanswerable records to a BYOD set"), the cell raises `IndexError: list index out of range`. The `except` catches only `TypeError`/`ValueError` and is not reached anyway. Separately, when that record's gold span already starts at offset 0, the "gold span at the wrong offset" probe is printed as `accepted`.
- **Consequence:** a learner bringing SQuAD 2.0-style data (about one-third unanswerable) has a substantial chance of a bare crash in Section 4, unrelated to their data's validity. Nothing downstream runs, which breaks the BYOD promise for the case the model exists for. The "accepted" probe line suggests the validator is broken when it is not.
- **Evidence:** direct execution (probe `byod.csv60_one_third_unanswerable_cell13_by_seed`). A 60-record CSV with every third record unanswerable, loaded with `load_byod_dataset` and split with `split_dataset`, crashes for seeds **0, 6 and 8 of 0–9** with `IndexError`. Probe `byod.wrong_offset_probe_with_gold_at_0` shows `verdict: accepted`.
- **Recommended correction:** in the template, build the probes from the first *answerable* training record, use an offset guaranteed to differ (e.g. `answer_start + 1`), and skip the wrong-offset probe with a printed note if no answerable record exists.
- **Acceptance check:** for the 60-record one-third-unanswerable CSV, cell 13 completes for every `SPLIT_SEED` in 0–9 and all four probes print `rejected`.
- **Spec:** DAT14, DAT19, REL12.

#### RQA-M5 — BYOD below about 50 records fails at Section 4, though the stated minimum is 8, and the error names the split's size, not the dataset's

- **Cell/section:** Prerequisites ("a dataset needs 8..20,000 records"), cell 0 BYOD paragraph, Section 4 cell 13 (`validate_dataset(part)` per split).
- **Observed:** `split_dataset` sends 20 % to test and 15 % to validation, and cell 13 then applies `validate_dataset` with `min_records=8` to **each** split. The result is that test needs at least 8 records and validation at least 8.
- **Consequence:** a learner with 8–45 records (a plausible first BYOD set) is refused with `ValueError: 6 records; 8..20000 are required`. That count is the validation split's, which contradicts the 40 records they uploaded and gives no corrective action.
- **Evidence:** direct execution, probe `byod.min_size_one_q_per_passage` (one question per passage): 8 → "split leaves 5 training records"; 12 → "2 records"; 20 → "4 records"; 30/38/40 → "6 records"; 45 → "7 records"; **50 → ok**. With several questions per passage (SQuAD-style), passage grouping shifts the threshold further.
- **Recommended correction:** state the real minimum (and the per-split minimum) in the Prerequisites and BYOD text, or validate the splits with `min_records=1` as `evaluate` already allows. Make the error name the split and the overall size required (`samples.py` `split_dataset` / template cell 13).
- **Acceptance check:** the stated minimum dataset size passes Section 4. A smaller set fails with a message that names the split, its size and the total record count needed.
- **Spec:** DAT12, DAT19, DAT14.
